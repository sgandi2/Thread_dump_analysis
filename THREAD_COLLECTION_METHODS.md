# ThreadHeap Guardian - Thread Dump Collection Methods

## Overview

ThreadHeap Guardian collects thread dumps from webMethods Integration Server using **standard Java diagnostic tools** that come with the JDK. We support three collection methods:

1. **jstack** (Primary method - Direct process attachment)
2. **jcmd** (Alternative method - More modern approach)
3. **File-based monitoring** (Production-ready - No special privileges required)

---

## 🛠️ Collection Methods

### **Method 1: jstack (Default)**

**What is jstack?**
- Standard JDK tool for generating thread dumps
- Comes with Java Development Kit (JDK)
- Works with any Java process
- Provides detailed thread state information

**Location:**
- Windows: `%JAVA_HOME%\bin\jstack.exe`
- Linux/Mac: `$JAVA_HOME/bin/jstack`

**Usage:**
```bash
# Basic usage
jstack <PID>

# Save to file
jstack <PID> > thread_dump.txt

# With ThreadHeap Guardian
python collect_with_jstack.py --pid 9584
```

**Advantages:**
- ✅ Fast and direct
- ✅ Real-time thread state capture
- ✅ Widely used and well-documented
- ✅ Works with all Java versions

**Limitations:**
- ⚠️ Requires same user context as target process
- ⚠️ May need administrator privileges on Windows
- ⚠️ Can fail with "Access Denied" for service accounts

**When to Use:**
- Development environments
- When you have appropriate permissions
- Quick diagnostic checks
- Interactive debugging sessions

---

### **Method 2: jcmd (Alternative)**

**What is jcmd?**
- Modern JDK diagnostic command-line tool
- Introduced in Java 7
- More versatile than jstack
- Supports multiple diagnostic operations

**Location:**
- Windows: `%JAVA_HOME%\bin\jcmd.exe`
- Linux/Mac: `$JAVA_HOME/bin/jcmd`

**Usage:**
```bash
# List Java processes
jcmd

# Generate thread dump
jcmd <PID> Thread.print

# Save to file
jcmd <PID> Thread.print > thread_dump.txt

# With ThreadHeap Guardian
python collect_with_jcmd.py --pid 9584
```

**Advantages:**
- ✅ More modern and actively maintained
- ✅ Additional diagnostic capabilities
- ✅ Better error messages
- ✅ Can list all Java processes

**Limitations:**
- ⚠️ Same permission requirements as jstack
- ⚠️ Requires Java 7 or later
- ⚠️ May have same access issues with service accounts

**When to Use:**
- Modern Java environments (Java 7+)
- When you need additional diagnostics
- Preferred over jstack for new implementations
- When jstack is not available

---

### **Method 3: File-Based Monitoring (Recommended for Production)**

**What is File-Based Monitoring?**
- Monitors Integration Server's diagnostics directory
- Reads thread dumps generated by Integration Server itself
- No direct process attachment required
- Production-ready approach

**How It Works:**
1. Integration Server generates thread dumps automatically
2. Files saved to: `IntegrationServer/instances/<instanceName>/logs/diagnostics/`
3. ThreadHeap Guardian monitors this directory
4. New files are automatically detected and analyzed

**Usage:**
```bash
# Monitor diagnostics directory
python start_monitoring_from_files.py --directory "C:\SoftwareAG\IntegrationServer\instances\default\logs\diagnostics"

# With custom instance
python start_monitoring_from_files.py -d "C:\SoftwareAG\IntegrationServer\instances\myinstance\logs\diagnostics"
```

**Advantages:**
- ✅ No special privileges required
- ✅ Works with service accounts
- ✅ Production-ready and stable
- ✅ No process attachment issues
- ✅ Leverages Integration Server's native diagnostics
- ✅ Automatic thread dump generation
- ✅ No performance impact on target process

**Limitations:**
- ⚠️ Requires Integration Server configuration
- ⚠️ Slight delay (depends on IS dump generation)
- ⚠️ Requires file system access

**When to Use:**
- ✅ **Production environments** (Highly Recommended)
- ✅ When Integration Server runs as service account
- ✅ When jstack/jcmd access is denied
- ✅ For continuous monitoring
- ✅ When stability is critical

## 🔧 Setup Instructions

### Setting Up jstack

**Windows:**
```cmd
# 1. Find Java installation
where java

# 2. Add jstack to PATH
set PATH=%PATH%;C:\Program Files\Java\jdk-11\bin

# 3. Verify
jstack -h

# 4. Use helper script
add_jstack_to_path.bat
```

**Linux/Mac:**
```bash
# 1. Find Java installation
which java

# 2. Add to PATH (add to ~/.bashrc or ~/.zshrc)
export PATH=$PATH:/usr/lib/jvm/java-11-openjdk/bin

# 3. Verify
jstack -h
```

### Setting Up jcmd

**Same as jstack** - jcmd is in the same directory as jstack in the JDK.

```bash
# Verify jcmd is available
jcmd -h

# List all Java processes
jcmd
```

### Setting Up File-Based Monitoring

**1. Configure Integration Server:**

Navigate to Integration Server Administrator:
- Settings → Resources → Thread Dump
- Enable automatic thread dump generation
- Set appropriate thresholds
- Configure output directory

**2. Verify Directory:**
```bash
# Check diagnostics directory exists
dir "C:\SoftwareAG\IntegrationServer\instances\default\logs\diagnostics"

# Or on Linux
ls -la /opt/softwareag/IntegrationServer/instances/default/logs/diagnostics
```

**3. Start Monitoring:**
```bash
python start_monitoring_from_files.py --directory "path/to/diagnostics"
```

## 🚨 Troubleshooting

### jstack "Access Denied" Error

**Problem:**
```
9584: Access is denied
```

**Cause:**
- Integration Server runs as different user (SYSTEM/service account)
- jstack runs as current user
- Windows security prevents cross-user process attachment

**Solutions:**

1. **Switch to File-Based Monitoring** (Recommended)
   ```bash
   python start_monitoring_from_files.py -d "path/to/diagnostics"
   ```

2. **Run as Administrator** (May not work with service accounts)
   ```bash
   # Right-click PowerShell → Run as Administrator
   jstack 9584
   ```

3. **Use jcmd Instead**
   ```bash
   jcmd 9584 Thread.print
   ```

### jcmd Not Found

**Problem:**
```
'jcmd' is not recognized as an internal or external command
```

**Solution:**
```bash
# Add JDK bin to PATH
set PATH=%PATH%;C:\Program Files\Java\jdk-11\bin

# Or use full path
"C:\Program Files\Java\jdk-11\bin\jcmd.exe" 9584 Thread.print
```

### File-Based Monitoring Not Detecting Files

**Problem:**
No thread dumps being detected

**Solutions:**

1. **Verify Directory Path:**
   ```bash
   dir "C:\SoftwareAG\IntegrationServer\instances\default\logs\diagnostics"
   ```

2. **Check Integration Server Configuration:**
   - Ensure automatic thread dump generation is enabled
   - Verify output directory is correct
   - Check file permissions

3. **Trigger Manual Thread Dump:**
   - Integration Server Administrator → Diagnostics → Generate Thread Dump
   - Verify file appears in diagnostics directory

## 📝 Best Practices

### For Development
1. Use jstack or jcmd for quick diagnostics
2. Keep JDK bin in PATH for easy access
3. Save dumps with timestamps: `jstack PID > dump_$(date +%Y%m%d_%H%M%S).txt`

### For Production
1. **Always use file-based monitoring**
2. Configure Integration Server for automatic dumps
3. Set appropriate thresholds (60s for hung threads)
4. Monitor diagnostics directory continuously
5. Archive old dumps regularly

### For All Environments
1. Test your collection method before deployment
2. Document which method you're using
3. Have fallback methods ready
4. Monitor collection success rates
5. Keep thread dumps for historical analysis
